# 대화형 프로그램·자료 업데이트

사용자가 프로그램 새 버전과 국채·거시 자료의 두 종류 업데이트 모두를 실행 시 자동 확인하고, 각각 적용 여부를 묻도록 요청했다. 기존 CLI에 `app` 모드를 추가했다. 명령을 생략해도 이 모드로 실행한다.

## 동작

- 프로그램: 고정 GitHub 저장소의 latest 정식 릴리스 확인 → 더 높은 안정 버전의 정확한 wheel 확인 → 사용자에게 설치 여부 질문 → 승인한 경우 다운로드·SHA-256/크기/패키지/버전 검증 → 현재 Python 환경에 pip 설치 → 종료 및 재실행 안내.
- 자료: 기존 실제 보고서의 수집 시각·기준일·개인/공개 모드를 확인 → 없거나 기준일이 달라지거나 수집 후 24시간이 지나면 자료 수집 여부 질문 → 승인한 경우 기존 수집/평가/게시 파이프라인 실행 → 보고서 열기.
- Enter·거절·EOF는 적용하지 않는다. 입력이 없는 환경은 설치와 수집을 모두 건너뛴다. 기존 `run`/`demo` 및 주간 Actions는 명시적 비대화형 명령으로 유지한다.
- 공개 모드에서 기존 개인 자료나 demo를 대신 열지 않는다. 거절 후 기존 결과를 열 때 수집 시각과 기준일을 표시한다. 수집 오류가 발생해도 과거 자료를 최신 자료로 대체하지 않는다.
- 프로그램 확인 통신이 실패하면 자료 갱신 선택을 계속 제공한다. 프로그램 설치 자체가 실패한 경우에는 종료 코드 2와 오류를 보여주고 종료한다. 성공한 설치 뒤에도 재실행 전의 메모리 코드를 계속 사용하지 않는다.
- editable 개발 설치는 자동 교체하지 않는다. 배포용 일반 설치와 Windows 시작 BAT를 안내했다. Windows의 Asia/Seoul 시간대 데이터는 tzdata 조건부 의존성으로 포함한다.

## 검증

- 테스트 75개 통과: 기존 63개 및 승인/거절/EOF/비대화형/모드 격리/판본·출처·해시·크기 검증, 릴리스 게이트 등 12개.
- 실제 PTY에서 자료 갱신 질문에 `n`을 입력해 수집 없이 종료하는 것을 확인했다.
- 비대화형 app은 네트워크 확인·설치·자료 수집 없이 종료했다. 기존 공개 demo도 보고서를 생성했다.
- 배포용 wheel을 빌드하고 별도 일반 설치 환경에서 app/demo를 실행했다.
- 격리된 가상환경에 검증용 0.0.9 fixture wheel을 설치한 뒤, 실제 대화형 승인 경로에서 0.1.0 wheel을 검증하고 실제 pip로 교체했다. 새 Python 프로세스에서 프로그램 코드와 설치 메타데이터가 0.1.0임을 확인했다. 이 실험에서는 GitHub 확인/다운로드만 로컬 wheel로 대체했다. GitHub를 통한 실시간 다운로드 성공의 증명은 아니다.
- 실제 latest GitHub API 확인은 통신 실패로 끝났고, 현재 버전 유지 안내를 확인했다. 새 릴리스가 생성되기 전에는 서버 배포·실시간 프로그램 다운로드 전체 경로를 확인할 수 없다.
- 독립 코드 리뷰에서 남은 actionable finding은 없었다. 새 프로그램 버전, 자료 품질·순위·재배포 게이트는 서로 다른 상태다.

## 배포 상태와 사용

`python -m sovereign_macro app`으로 실행한다. 질문은 터미널에 나타나며 정적 HTML 또는 이전 결과 ZIP에는 업데이트 실행 기능이 없다. 실행 시 확인하고 프로그램 종료 후 백그라운드에서 계속 확인하는 서비스는 아니다.

버전 태그 기반 `Stable program release` 워크플로는 main에 포함된 커밋, 태그와 두 버전 필드의 일치, wheel 설치 및 테스트를 검증한 후 배포용 wheel을 게시하도록 구성했다. 실제 main 병합·태그 생성·릴리스 게시를 이 작업에서 수행하지 않았다. 설치 로직의 로컬 검증과 GitHub 서버 배포 완료를 구분한다.
